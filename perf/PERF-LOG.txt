  BUG-001  [FIXED]  CRITICAL — Background indexing freezes the entire API
--------------------------------------------------------------------------------
  Area     : backend/app/services/indexing_service.py
  Found by : k6 index-contention.js
  Severity : CRITICAL — full outage, 13m01s, includes /health

  EVIDENCE
    k6 timeline, 3 VUs polling 6 endpoints, index triggered at t+50s:
      t+s   n   fail  avg ms    p95 ms    max ms
       40  169    0     20.2       64.0     177.2     <- healthy ~30 req/s
       70    3    3  29998.3   29998.4   29998.4     <- all timing out
      250    3    3  29994.7   29995.3   29995.3
    Every failure is exactly 29,999ms = the client timeout. Zero successes after
    t+50s.

    Backend log correlation:
      17:20:10.452584Z  indexing_started
      17:32:59.310890Z  files_found count=44      (+12m49s)
      17:33:11.100497Z  indexing_completed         (+13m01s total)

    Independently reproduced: indexing Semantic-Code-Search produced a separate
    145-second window with zero successful responses.

  ROOT CAUSE (revised 2026-10-02 — see correction below)
    index_repository() is `async` but performs synchronous blocking work directly
    on the event loop:
      indexing_service.py:36  scan_repository()      — synchronous FS walk
      indexing_service.py:53  Path.read_text()        — synchronous file read
      indexing_service.py:65  extract_code_units()   — synchronous tree-sitter parse
    It is dispatched via FastAPI BackgroundTasks (repository_api.py:104) which runs
    IN THE SAME single Uvicorn worker. With no await point during those calls, the
    single-threaded event loop cannot serve any other request — not even /health.

    CORRECTION (2026-10-02). This entry originally claimed "~17.5 seconds of
    blocking CPU per file" and blamed tree-sitter. Direct measurement disproves
    that. What was actually slow:
      - tree-sitter parses ~2.4 ms per file and RELEASES THE GIL, so it was never
        the bottleneck and is not inherently unsuitable for threads.
      - the real cost was Path.rglob("*") inside scan_repository, which walked
        705,868 directory entries to find ~1,332 files: 16.91s run natively from
        D:\Code\Projects, and 12m49s under the Docker bind mount. That matches the
        +12m49s to files_found in the log excerpt above exactly.
    The conclusion (blocking work on the event loop) stands; only the cost model
    was wrong. Fixing the traversal is what actually removed the stall.

  IMPACT
    Complete unavailability for the duration of any index job. The Docker healthcheck
    (GET /health every 10s, 5 retries) also fails, but `restart: unless-stopped` keeps
    the container alive, so the failure is SILENT in Docker while the API is dead.

  EVIDENCE
    Indexing began by calling delete_collection("code_embeddings") before every
    run. Because the collection is shared by all repositories, indexing one repo
    erased the vectors of every other repo. Observed directly: after indexing a

    others' indexing and the delete removed exactly IronVill's 13 points.

  BUG-013  [FIXED]  HIGH — Repository deletion left orphan vectors behind

  Severity : HIGH (unbounded storage growth, misleading search if filters relax)

  EVIDENCE

    points) predates the fix and is still present; see 5.4.

================================================================================
  SECTION 3 — ANALYSIS
================================================================================

  3.1 THE CENTRAL PROBLEM
  ------------------------------------------------------------------------
  The service runs ONE Uvicorn worker on ONE event loop, and that loop is blocked
  by synchronous code on both the background path (BUG-001) and the request path
  (BUG-002). Everything else in this log is a secondary effect.

  This is why the measurements look contradictory at first glance:
    - 27,000 requests with ZERO errors, yet a total outage exists.
    - A trivial query (GET /api/repositories) taking 773 ms under load.
    - p95 healthy (144 ms) while p99 is 29,994 ms.
  There is no error condition. The loop is simply not being scheduled. A load
  generator with a 30 s client timeout reports this as "a few failures"; a real user
  sees a hung UI, then a gateway timeout.

  3.2 WHY THE EXISTING THRESHOLDS UNDERSTATED THIS
  ------------------------------------------------------------------------
  The original thresholds were p95 < 5000 and success > 98%. The contention run
  scored p95 = 144 ms (PASS) and success = 98.44% (PASS) — while the server was
  completely dead for 13 minutes. Percentile thresholds structurally cannot see an
  outage if the outage is short relative to total samples.

  CONCLUSION: percentile SLOs are necessary but not sufficient. A hard
  availability gate is also required. Two changes proposed:
    - a dedicated "max request duration" threshold, not just percentiles
    - a zero-tolerance counter for requests exceeding a hard budget
      (blocked_requests already exists for this purpose and did fire)

  3.3 FIX ORDERING
  ------------------------------------------------------------------------
  Ranked by (severity x reach) / effort, cheapest high-impact first:

    1. BUG-002 AsyncQdrantClient          tiny diff, unblocks the REQUEST path
    2. BUG-001 offload blocking calls    small diff, fixes the OUTAGE
    3. BUG-006 batch the N+1              small diff, ~10 fewer round-trips/search
    4. BUG-005 tune the pool              one line, removes a hidden ceiling
    5. BUG-003/004 fix provider routing   correctness, not perf
    6. BUG-008 paginate graph             prevents future blowup
    7. BUG-009 batch embeddings           indexing speed
    8. BUG-010 align versions             hygiene

  Items 1-4 are independent and can all land together. 1+2 together should move the
  API from "unavailable during indexing" to "degraded during indexing".

  3.4 EXPECTED OUTCOME AFTER FIXES 1-4 (targets, to be measured)
  ------------------------------------------------------------------------
    Metric                        Now            Target
    ----------------------------------------------------------------------------
    Search throughput             8.26 req/s     >= 20 req/s (pool-bound relief)
    Read throughput               60.2 req/s     >= 80 req/s
    Search p95 @ 30 VUs           3.76 s         <= 2.5 s
    API availability during index 0%            100%
    Max request duration          29,994 ms     < 5,000 ms
    DB round-trips per search     11             2

  NOTE: search throughput remains bounded by serial Ollama inference unless BUG-009
  is also fixed. That is an infrastructure limit, not an application defect.

  3.5 RISKS
  ------------------------------------------------------------------------
    - AsyncQdrantClient is a different client with a different API surface. Needs a
      real search against a populated collection to verify, not just a health check.
    - Offloading parse work to threads still holds the GIL during tree-sitter C calls
      in places. A worker process is the only fully robust answer; threads are a
      large improvement, not a complete fix.
    - Raising pool_size increases Postgres load. Postgres max_connections must be
      checked (default 100) before choosing numbers.
    - Fixing BUG-003 will route explain/trace to Ollama, which is SLOWER than Gemini
      for generation (77 s observed). Latency for those endpoints will get worse
      before it gets better; that is correct routing, not a regression.
